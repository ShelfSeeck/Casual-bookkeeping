二、同步靠四对键值对
sync_id ⇔ sync_id＝ 定位同一条业务记录（前端主键 = 后端唯一键），前后端共用
operation_id ⇔ operation_id＝ 一次业务动作的幂等键：断网重试不重复写；也是撤回关联键
server_seq ⇔ appliedServerSeq＝ 后端操作序号 server_seq（全局递增）⇔ 前端已应用到哪的游标。Pull 起点，允许 gap，只要求严格大于
row_version ⇔ base_version＝ 冲突检测：Push 时客户端交的 base_version 若 ≠ 服务端当前 row_version → conflict
account_phone ⇔ account_phone＝ 账户隔离：前后端所有表都带它，Pull/Push 只处理当前账户的数据
三、数据怎么流动
1
本地写入（离线可用）
页面 → 一次 IndexedDB 事务：改业务表 + 写 operations(pending) + 写 outbox(pending)。保存即本地生效，不依赖网络。
▼
2
Push（先推）POST /sync/push
把 outbox 按 queueId 顺序整批推给后端。后端逐条：查 operation_id 幂等 → 比对 base_version vs row_version → 写业务表 + 递增 row_version + 写正式历史（拿新 server_seq）。返回逐条结果。
▼ 逐条结果
3
按结果分类处理
accepted → 删 outbox，operations 标 synced
conflict → 保留 outbox；Theirs 从响应来，配本地 Base/Ours 三方对比，用户合并后生成新 operation 再推
rejected → 保留 outbox，等用户修正命令
▼
4
outbox 全清空后 Pull（后拉）GET /sync/pull?after=appliedServerSeq
拉 server_seq > after 的自己 + 别人 + AI 的操作。每条带 after_json（结果快照）+ after_version。前端一个事务：把 after_json 写进业务表 + 写 operations 镜像 + appliedServerSeq 推进。事务失败整页回滚，下次重拉。
▼
5
新设备首登 → bootstrap GET /sync/bootstrap
本地为空时，分页下载四张业务表当前状态 + snapshot_seq。写完快照后 appliedServerSeq = snapshot_seq，再立即 Pull 补上增量。
四、三条关键规则
  • 每轮同步 先 Push 后 Pull；outbox 里还有 pending/conflict/rejected 就只 Push 不 Pull，保证 Pull 不会覆盖未决修改。
  • 本地业务表 只等于服务端确认过的状态；未决修改只存在 outbox，冲突解决后才进业务表。
  • 会话失效（token 过期/被踢）不清本地数据，只停同步去登录页；主动登出才清活跃账户，本地库保留。
